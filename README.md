# Домашнее задание к занятию «Репликация и масштабирование. Часть 2» - Яковлев Кирилл

### Задание 1
Опишите основные преимущества использования масштабирования методами:

    активный master-сервер и пассивный репликационный slave-сервер;
    master-сервер и несколько slave-серверов;
Дайте ответ в свободной форме.

### Решение 1

1. Активный Master-сервер и пассивный репликационный Slave-сервер (Active Master — Passive/Standby Slave)
В такой конфигурации весь рабочий трафик приложения (и запись, и чтение) направляется на единственный активный Master-сервер, а пассивный Slave-сервер в фоновом режиме синхронизирует данные (получает журнал предзаписи WAL или binlog), но не обслуживает пользовательские запросы до момента аварии.

Отказоустойчивость и быстрое восстановление (High Availability / Failover): Главное назначение пассивной реплики — горячий резерв. Если основной Master-сервер выходит из строя (аппаратный сбой, повреждение диска), пассивный Slave берет на себя роль нового Master-сервера (выполняется процедура promote). Время простоя системы (RTO) сокращается с часов (как при восстановлении из обычного бэкапа) до секунд или минут.

Предсказуемая производительность после аварии: Поскольку пассивный Slave в штатном режиме не нагружен клиентскими запросами на чтение, ресурсы Master-сервера не маскируются за счет реплики. В момент переключения трафика на резервный сервер гарантированно хватит вычислительной мощности (CPU, RAM, IOPS), чтобы выдержать 100% боевой нагрузки.

Безопасное резервное копирование и обслуживание без деградации сервиса: Тяжелые операции — снятие полных дампов базы данных, проверка целостности таблиц или аналитические выгрузки — можно выполнять на пассивном Slave-сервере. Это избавляет боевой Master от блокировок таблиц, просадок по дисковому вводу-выводу и вымывания кэша из оперативной памяти.

Тестирование обновлений и миграций: На пассивной реплике можно безопасно проверить установку патчей СУБД или перестроение тяжелых индексов перед тем, как переключить на неё основной трафик.

2. Master-сервер и несколько Slave-серверов (Master — Multiple Active Slaves)
В этой топологии операции модификации данных (INSERT, UPDATE, DELETE) и критичные к задержке чтения идут на Master-сервер, а основная масса запросов на чтение (SELECT) распределяется балансировщиком нагрузки между несколькими активными Slave-серверами.

Горизонтальное масштабирование чтения (Read Scaling): В большинстве информационных систем и веб-сервисов на чтение приходится 80–95% всех запросов, а на запись — лишь 5–20%. Добавление новых Slave-серверов позволяет практически линейно наращивать пропускную способность системы по чтению без необходимости покупать более дорогое «железо» для одного сервера.

Изоляция аналитической нагрузки (OLTP vs OLAP): Один или несколько Slave-серверов можно выделить специально под построение сложных отчетов, работу BI-систем и тяжелые поисковые запросы. В результате «тяжелые» аналитические выборки не тормозят быстрые пользовательские транзакции на Master-сервере и остальных читающих репликах.

Высокая живучесть и плавная деградация: Выход из строя одного из Slave-серверов вообще не заметен для пользователей — балансировщик (например, HAProxy или ProxySQL) автоматически исключает упавший узел из пула чтения и перенаправляет запросы на оставшиеся реплики. При падении самого Master-сервера один из наиболее актуальных Slave-узлов повышается до нового Master-а, а остальные реплики перенастраиваются на него, сохраняя работоспособность читающего кластера.

Географическое распределение (снижение Latency): Slave-серверы можно разместить в разных регионах или дата-центрах ближе к конечным пользователям, чтобы они читали данные с минимальной сетевой задержкой.

### Задание 2
Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:

 пользователи,
 книги,
 магазины (столбцы произвольно).
Опишите принципы построения системы и их разграничение или разбивку между базами данных.

Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.

### Решение 2
Принципы построения и разграничения данных
Для нашей системы применяется комбинированный подход: разделение таблиц по разным базам данных (вертикально) с одновременным разбиением строк внутри каждой таблицы (горизонтально по шардам).

Таблица «Пользователи» (users):

Принцип: Шардирование по уникальному идентификатору пользователя (user_id), например, по остатку от деления (user_id % 2).

Разграничение: Выделена в отдельный кластер БД, так как здесь критична скорость авторизации и высокий темп операций записи/обновления профилей.

Таблица «Книги» (books):

Принцип: Шардирование по жанру или диапазону (genre_id).

Разграничение: Каталог книг генерирует 95% поискового трафика на чтение. Шардирование по категориям позволяет отправлять поисковые запросы не во всю базу, а сразу в нужный тематический шард.

Таблица «Магазины» (stores):

Принцип: Географическое шардирование по региону (region_id).

Разграничение: Небольшой справочник, который логично разделить по регионам присутствия, чтобы пользователи искали магазины своего города локально.

2. Блок-схема расположения компонентов
```

                  [ Клиент / Приложение ]
                             |
                             v
               [ Роутер / Балансировщик запросов ]
                             |
        +--------------------+--------------------+
        |                    |                    |
        v                    v                    v
  [ БД «Пользователи» ]  [ БД «Книги» ]    [ БД «Магазины» ]
  (Шарды по user_id)     (Шарды по genre)  (Шарды по region)
        |                    |                    |
   +----+----+          +----+----+          +----+----+
   |         |          |         |          |         |
   v         v          v         v          v         v
[Шард 1]  [Шард 2]   [Шард 1]  [Шард 2]   [Шард 1]  [Шард 2]
(M + S)   (M + S)    (M + S)   (M + S)    (M + S)   (M + S)
```

(Где M — Master-сервер записи, S — Slave-сервер чтения)

3. Режимы работы серверов 
Роутер (ProxySQL / HAProxy): Работает в режиме Stateless-маршрутизации. Анализирует входящий SQL-запрос, определяет нужный шард по ключу (user_id, genre_id или region_id) и направляет запись на Master, а чтение — на Slave.

Master-серверы (по одному на каждый шард): Работают в режиме Read/Write. Принимают все операции изменения данных (INSERT, UPDATE, DELETE).

Slave-серверы (по одному или два на шард): Работают в режиме Read-Only. Обслуживают запросы на чтение (SELECT), синхронизируясь с Master-сервером в асинхронном или полусинхронном режиме.
